# 설계안 초안: 에이전트 인사 — 필요한 에이전트를 찾고, 만들고, 평가해 재계약·퇴출하는 절차

> 상태: 초안(Proposed) · 작성 2026-11-23 · 발굴·정의 도구 구현 2026-11-23(10절) · 대상: 데스크(`agents/orch.md`), `brief`, 영역 프로파일
> 함께 읽을 것: [`area-lead-design.md`](area-lead-design.md) — 영역 담당(판단을 맡는 자리). 이 문서는 그 아래에서
> **일을 하는 자리**를 다룬다. 이 문서는 설계만 하고 코드는 고치지 않는다.
> 공개 저장소이므로 절차와 숫자만 적는다. 세션별 근거 경로는 이 기기의 로컬 기록
> (`~/.local/share/cmux/hr/scan-2026-11-23.md`)에만 둔다.

## 1. 요약

- **pstack 은 에이전트를 발굴·배치·평가하는 도구가 아니다.** 역할 9개(일의 종류)에 모델과 추론 단계를 고정하는
  설정 한 장과, 작업마다 새 서브에이전트를 띄우는 규칙이 있을 뿐이다. 역할의 성과를 기록하거나 역할을 없애는
  장치는 없다. 다만 **이력에서 규칙을 캐는 부품**(`/automate-me`, `/reflect`, `/correct`)과 **바꾸기 전에 블라인드로
  비교하는 부품**(eval 플레이북, arena 의 다른 회사 모델 심판)은 쓸 만하다. 인사 절차는 이 부품들을 단계에 끼워
  쓰고, 빠진 부분(명부·계약·평가 기록·퇴출)만 새로 정한다(2절).
- 이 기기에서 '에이전트'는 사람이 아니라 **한 종류의 일에 대한 묶음**(지시문 + 도구 권한 + 모델 + 기록)이다. 모델은
  어디서나 같으므로 고용·퇴출은 이 묶음을 만들고·좁히고·치우는 일이다(영역 담당 설계 2절과 같은 원칙).
- 이 기기의 기록(4절)에서 손이 가장 많이 가는 일은 **먼저 확인받는 업무 영역**의 검증 작업이다(사용자 턴과
  교정의 대부분). 에이전트 도구 영역 안에는 새 에이전트가 필요한 큰 고통이 보이지 않는다 — 그쪽 문제는
  도구(`brief audit` 등)로 풀리고 있다.
- 그래서 **첫 에이전트는 그 업무 영역의 '실험 계획 검토자'를 권고 전용으로** 만드는 것을 1순위로 제안하되, 그 영역은
  먼저 확인받는 영역이라 사용자 확인 뒤에 만든다. 사용자가 원하지 않으면 2순위(리서치 범위 확인자)로 간다(8절).

## 2. pstack 검토

검토 대상: pstack 0.15.43(설치 위치는 Claude Code 플러그인 캐시), 역할 설정 `~/.claude/rules/pstack-models.md`,
11-18 설치 세션의 결론("앱 코드 개발용이라 몇 개만 골라 쓴다").

### 2.1 pstack 이 역할을 다루는 방식

| 단계 | pstack 의 방식 | 근거(스킬) |
|---|---|---|
| 정의 | 역할 = 일의 종류 라벨 9개(`feature, refactoring`, `bug-fix`, `perf-issue`, `hillclimb`, `judgment and prose`, `arena runners`, `arena cross-judge pool`, `swarm workers`, `interrogate reviewers`). 각 줄은 모델과 추론 단계만 정한다. 지시문은 역할이 아니라 플레이북 22개와 원칙 스킬에 있다 | `setup-pstack` 5단계, `poteto-mode` Subagents 절 |
| 배정 | 사용자가 `/poteto-mode` 를 부르면 그 채팅이 일을 플레이북 하나에 맞추고, 단계마다 그 역할 줄의 모델로 **새** 서브에이전트를 띄운다. 서브에이전트 첫 줄은 언제나 `worker.md` 를 읽으라는 지시다(규칙 전달 경로) | `poteto-mode` Non-negotiables, "Fresh subagents by default" |
| 평가 | 산출물만 평가한다: arena 는 다른 회사 모델 심판 한 명이 기준표로 채점, interrogate 는 실행으로 증명된 발견만 남김, eval 플레이북은 후보에게 시험임을 숨기고 심판에게 모델 이름을 숨긴다 | `arena` Phase C, `interrogate`, `playbooks/eval.md` |
| 개선 | `/automate-me`: 대화 기록을 조각으로 나눠 병렬로 캐고, 두 조각 이상에서 보인 신호만 남겨 사용자 한 명의 `-mode` 스킬을 만든다. `/reflect`: 한 세션의 교훈을 기존 스킬 수정으로. `/correct`: 두 번 일어난 실수를 구조 → 타입 → lint → 시험 → 문서 순으로 막는다 | 각 SKILL.md |
| 퇴출 | **없음.** 역할의 모델은 사용자가 `/setup-pstack` 을 다시 돌려 바꾼다. 역할별 성과 기록, 계약 기간, 없애는 기준이 없다 | — |

### 2.2 "pstack 이 그걸 돕는 도구" 라는 기대와 다른 점

| 기대 | 실제 |
|---|---|
| 필요한 에이전트를 찾아 준다 | `/automate-me` 는 **사용자 한 명의 작업 습관**을 스킬 하나로 만든다. 일의 종류별로 어떤 에이전트가 필요한지 찾지 않는다. `/correct` 는 실수 종류를 찾지만 결과는 에이전트가 아니라 저장소 규칙이다 |
| 에이전트를 만든다 | 에이전트 정의는 2개(`poteto-agent`, `comment-sicko`)뿐이고 만드는 절차도 없다. 스킬 작성은 Cursor 의 `create-skill` 에 맡긴다(Claude Code 에서는 `skill-creator`) |
| 평가해 재계약·퇴출한다 | 평가는 **한 번의 산출물**에 대한 것이다. 같은 역할을 기간에 걸쳐 재는 기록이 없다 |
| 역할을 배정한다 | 배정은 한 채팅 안의 플레이북 단계 → 서브에이전트까지다. 여러 세션·영역 사이의 배치는 이 기기에서는 데스크가 한다 |

결론: pstack 은 인사 기능의 **부품 상자**다. 인사 기능 자체(명부, 계약, 기간 평가, 퇴출)는 이 기기의 기존 루프 —
데스크 교훈(`ok`/`miss` 와 졸업), 가드 루프(고정 시험지·주간 holdout·자동 되돌림), 영역 담당 계약 — 에서 가져온다.

### 2.3 가져올 것

| 부품 | 인사 절차에서 쓰는 곳 |
|---|---|
| `/automate-me` 의 채굴 방식: 기간을 조각으로 나눠 병렬로 캐고, **두 조각 이상**에서 보인 신호만 올린다 | 발굴(5.1). 한 번 보인 신호는 후보로 올리지 않는다 |
| `/correct` 의 "두 번 일어나면 한 종류" 와 **구조 → 타입 → lint → 시험 → 문서** 순서 | 발굴 신호의 기준, 그리고 '에이전트를 만들지 말고 도구로 막을 일' 을 거르는 기준(5.2 의 형태 고르기) |
| `/reflect` 의 거름망: 6개월 뒤에도 맞고, 다음 에이전트의 행동을 바꾸고, 기존 스킬로 갈 수 있는 것만. Accepted / Rejected / Backlog 로 나눠 승인 전에는 고치지 않음 | 평가 뒤 역할 카드를 고칠 때(5.4) |
| eval 플레이북의 블라인드 비교: 후보에게 시험임을 숨기고, 심판은 모델 이름을 모르고, 두 안을 한 번에 같은 기준으로 채점 | 수습 판정(5.3)과 재계약 때의 표본 비교 |
| arena 의 심판 규칙: 만든 쪽과 **다른 회사 모델**이 채점(같은 회사 모델은 같은 쪽으로 기운다) | 평가 심판. 이 기기에서는 Codex 가 그 자리다 |
| `worker.md` 패턴: 띄우는 모든 에이전트의 첫 줄이 규칙 파일을 읽게 한다 | 배치 때 브리프 첫 줄에 역할 카드 경로(영역 담당 설계 8절 4번의 프로파일 줄과 같은 방식) |
| `setup-pstack` 의 "역할 한 줄 = 모델 한 줄" 설정 | 역할 카드의 `model` 칸. 기본은 `pstack-models.md` 의 해당 줄을 따른다 |

### 2.4 버릴 것

- **`poteto-mode` 플레이북 묶음 전체를 기본 작업 방식으로 쓰는 것.** 앱을 마음대로 재현하고 PR 로 내보내는 흐름이라
  운영 환경 일과 맞지 않는다(11-18 결론 그대로).
- **Autonomy 절의 "팀 채팅·티켓 갱신은 묻지 않고 진행"** 과 `worker.md` 의 "사람에게 묻는 도구를 쓰지 마라".
  이 기기의 선(push·티켓·바깥 전달은 사용자)과 정면으로 부딪힌다.
- **세 회사 패널을 기본값으로 쓰는 것.** 역할마다 패널 3개는 비용이 크다. 패널은 수습 판정과 재계약 표본에만 쓴다.
- **역할을 일의 종류 라벨로만 두는 것.** 라벨만으로는 무엇을 맡고 무엇을 안 맡는지, 언제 잘했는지 알 수 없다.
  이 기기의 역할은 카드(5.2)를 가진다.
- **미뤄 둔 'pstack 식 라우터'**(에이전트 작업공간의 explain-diff 결정 기록에 남은 항목): 따로 만들지 않는다.
  `poteto-mode` 의 플레이북 고르기는 한 채팅 안의 라우터이고, 이 기기에서 세션 사이의 라우팅은 데스크 배치 +
  영역 분류 + 명부의 트리거(5.2)가 맡는다. 라우터를 하나 더 두면 같은 결정을 두 곳에서 하게 된다.

## 3. 이 기기에서 '에이전트'의 네 가지 형태

| 형태 | 예 | 언제 맞나 |
|---|---|---|
| 스킬 | `explain-diff`, `guard-review` | 세션이 스스로 따르면 되는 절차. 컨텍스트를 나눌 필요 없음 |
| 에이전트 정의(`agents/*.md`) | `orch`, 트래커 정리 에이전트 | 도구 권한을 좁히거나 메인 세션의 컨텍스트를 지켜야 할 때 |
| 영역 담당 | 영역 A 의 `brief lead` | 일이 아니라 **판단**을 맡길 때(영역 담당 설계) |
| 루프 | 가드 루프 | 결과를 매일 숫자로 잴 수 있을 때 |

인사는 이 네 형태를 모두 대상으로 한다. 이미 인사 사건은 기록 없이 일어나고 있다:

- **퇴출 2건**: 오케스트레이터는 sib 가 그 일을 흡수해 퇴출, 자동 승인 데몬은 명령을 보지 못한 채 승인하고
  사용자 대신 질문에 답해 퇴출 → **기록 없이 되살아났다가** 다시 퇴출(결정 기록은 하위 계층에 있다).
- **고용 1건**: 트래커 정리 에이전트는 만들어졌지만 쓰임새나 성과를 재는 기록이 없다.

되살아난 데몬 사건이 이 설계가 막으려는 것이다: 퇴출 기록이 한 곳에 없으면 같은 실수로 다시 고용한다.

## 4. 이 기기의 기록에서 뽑은 후보

**자료**(3주): Claude Code 세션, Codex 기록, sib 브리프, 데스크 문서의 `결정 필요`. 일의 종류별 세션 수·사용자 턴·
교정 수와 세션 경로는 이 기기의 로컬 기록(`~/.local/share/cmux/hr/scan-<날짜>.md`)에만 둔다. 교정 = 짧은 사용자 턴 중
"아니·왜·다시…" 로 시작하는 것.

표의 모양(값은 예시):

| 일의 종류 | 세션 | 사용자 턴 / 교정 | 이미 있는 것 | 반복되는 문제 |
|---|---|---|---|---|
| 업무 영역의 검증(실험·설계·배포 검토) | 가장 많음 | 가장 많음 | 운영 조회 스킬 | 시간 예산을 넘김, 브리프에 없는 상황을 지어냄, 범위를 바꿈 |
| 에이전트 도구 개발 | 많음 | 교정 적음 | `orch`, `dispatch` | 데스크 결함이 이 일을 만든다 — 도구로 고치는 중 |
| 리서치(일반·OSS) | 매주 | 교정 몇 번 | 리서치 스킬 | 범위 오독(내부 자료 / 일반 지식) |

### 4.1 후보 판정

후보 기준(5.1 과 같음): 2주에 3회 이상 생기고, 같은 교정이나 같은 재설명이 2회 이상 있고, 맡길 지시가 안정적이고,
결과를 확인할 수 있다.

| 후보 | 판정 | 이유 |
|---|---|---|
| **업무 영역의 실험 계획 검토자** | **1순위 · 사용자 확인 필요** | 교정이 가장 많고 같은 종류가 반복된다. 실험을 **돌리기 전에** 계획을 체크리스트로 읽는 일이라 읽기 전용·권고 전용으로 만들 수 있다. 결과도 확인된다(그 실험에서 같은 교정이 다시 나오는가). 먼저 확인받는 영역이라 만들기 전에 묻는다 |
| 리서치 범위 확인자 | 2순위 | 매주 생기고, 범위(내부/일반/OSS)를 매번 다시 설명한다. 다만 고통이 작다. 스킬 한 줄로 끝날 수도 있다 |
| 데스크 완료 감사 | 만들지 않음 | 이미 도구(`brief audit`)와 다른 세션이 맡고 있다. `/correct` 순서상 도구로 막을 수 있는 일은 에이전트로 만들지 않는다 |
| 교정이 없는 유지 일 | 만들지 않음 | 고통이 없는 곳에 역할을 두면 유지비만 생긴다 |

## 5. 절차

```
발굴 ──→ 정의 ──→ 수습 ──→ 평가 ──→ 판정(재계약 · 확대 · 축소 · 퇴출 · 흡수)
 ↑                                        │
 └──── 수습 판정 7일, 그 뒤 계약 판정 14일마다 ────┘
```

### 5.1 발굴

- **입력**: 지난 2주의 세션 기록(Claude·Codex), sib 브리프, 데스크 문서의 `결정 필요`, `brief note`, 데스크 교훈.
- **방법**: `/automate-me` 의 채굴 방식. 기간을 2~3 조각으로 나눠 조각마다 일의 종류·교정·재설명을 세고,
  두 조각 이상에서 보인 것만 남긴다. 세는 일은 스크립트로 한다(수치를 다시 돌려 볼 수 있게. pstack 의 *Build the lever*).
- **후보 신호**(하나라도): 같은 종류의 일이 2주에 3회 이상 / 같은 교정이 2회 이상(`/correct` 의 기준) / 사용자가 같은
  맥락을 2회 이상 다시 설명 / 데스크가 같은 종류의 결정을 2회 이상 사용자에게 넘김.
- **출력**: 4절 같은 표 하나를 로컬 기록(`~/.local/share/cmux/hr/scan-<날짜>.md`)에 남긴다. 세션 경로와 사내 이름은
  이 로컬 파일에만 둔다.

### 5.2 정의 — 역할 카드

후보 하나를 고르면 먼저 **형태**를 고른다. `/correct` 의 순서를 따른다: 도구나 lint 로 막을 수 있으면 에이전트를
만들지 않는다. 남는 것 중에서 3절 표로 스킬 / 에이전트 정의 / 영역 담당 / 루프를 고른다.

그다음 역할 카드를 쓴다. 카드는 그 형태의 파일(스킬이면 `SKILL.md`, 에이전트면 `agents/<이름>.md`) 맨 위의 머리말과
명부의 한 줄로 나뉜다.

| 칸 | 내용 |
|---|---|
| 이름, 형태 | `widgetdb-plan-reviewer`, 에이전트 정의 |
| 영역 | 영역 프로파일의 이름. 권한은 **그 영역의 권한표를 넘을 수 없다** |
| 맡는 일(트리거) | 언제 부르는가. 예: 실험 브리프가 만들어진 뒤, 실행 전 |
| 맡지 않는 일 | 예: 실행, 운영 변경, 사용자 대신 답하기 |
| 도구 권한 | 읽기 전용 등. 좁을수록 좋다 |
| 모델 | `pstack-models.md` 의 해당 줄을 따르거나 한 줄로 적는다 |
| 완료 판정 | 결과가 맞았는지 무엇으로 보나 |
| 지표 | 5.4 의 표에서 고른다 |
| 근거 | 발굴 기록의 날짜와 줄 |
| 계약 | 시작일, 수습 판정일(7일 뒤, 5.3), 재평가 모델(있으면, 5.6) |

**층(L1/L2/L3)**: 절차와 카드 형식은 L1(이 저장소). 회사 일에 쓰는 카드와 명부는 L2 페르소나나 L3 도메인 팩, 또는
이 기기의 로컬 파일에 둔다. 이 저장소에는 회사 일의 카드를 넣지 않는다.

**명부**: 영역 프로파일 옆에 로컬 파일 하나(`~/.config/cmux/orch-roster.md`, 씨앗은 `cmux/seeds/`)를 두고, 영역마다
역할 한 줄과 그 역할의 기록을 둔다. 형식은 영역 결정 기록과 같은 한 줄씩:

```
- <역할> | <형태> | <영역> | 상태: 수습|계약|축소|퇴출 | 시작 MM-DD | 판정 MM-DD | 카드: <경로>
- MM-DD | <역할> | use | ref:<세션> | ok|miss|corrected
```

고용과 퇴출 자체는 그 영역의 Decision log 에 새 종류 `hire`·`retire` 로 한 줄씩 남긴다.

### 5.3 수습

일정은 하나다. **수습 7일 → 수습 판정 → 계약 뒤 14일마다 판정(5.5)**. `agent-scout install` 이 명부에 적는
`판정` 날짜(설치일 + 7일)가 수습 판정일이다. 계약 판정은 수습 판정일부터 14일 간격이고, 위원회 정기 소집(기본 14일)과
같은 주기다. 같은 줄에 계약 전체를 적는다: `판정 MM-DD | 연장 시 MM-DD | 계약 판정 MM-DD부터 14일마다 | 재평가 모델: <모델|->`
(재평가 모델은 `--reeval` 또는 카드 `contract` 의 "re-evaluation model: X").

```
설치 ──7일──→ 수습 판정 ──14일──→ 계약 판정 ──14일──→ 계약 판정 …
               │  표본 부족이면 한 번만 7일 연장
               └─ 카드에 재평가 모델이 있고 판단을 틀렸으면 5.6
```

- 수습 동안은 **권고만** 한다(결과를 세션이 쓸지 사용자가 정한다).
- 데스크가 그 일의 세션 브리프 첫 줄에 카드 경로를 넣거나(`worker.md` 패턴), 세션이 서브에이전트로 부른다.
  **부르는 곳이 없으면 `uses` 가 0 에 머물러 판정할 수 없다.** 투입 확인(6절) 때 카드의 `triggers` 가 실제로 어디서
  불리는지(훅·데스크 지시·브리프 첫 줄)를 함께 정한다.
- 블라인드 비교(eval 플레이북): 같은 과거 일 3건 이상을 역할 있이 / 없이 다시 돌려, 다른 회사 모델 심판이 이름을
  모른 채 카드의 완료 판정으로 채점한다.

수습 판정(7일 창, 지표는 5.4 의 세는 곳으로 센다):

| 결과 | 조건 | 결정 |
|---|---|---|
| 계약 | `uses` ≥ 3, 판정된 호출 중 `ok` ≥ 2/3, `corrected` ≤ 1, 블라인드 비교에서 역할 쪽이 같거나 낫다 | 데스크가 기록하고 알린다 |
| 수습 연장(한 번, 7일) | `uses` < 3 — 표본이 모자라 판정할 수 없다 | 데스크가 정하고 알린다 |
| 다른 모델로 재평가 | 카드 `contract` 에 재평가 모델이 있고, `ok` < 2/3 이며 miss 가 판단 잘못이다 | 5.6 |
| 해체 | 연장한 뒤에도 14일 합계 `uses` < 3 | 사용자 |
| 퇴출 | 그 밖(판단을 틀리거나 블라인드 비교에서 역할 쪽이 못하다) | 사용자 |

### 5.4 평가

자기 보고로 재지 않는다. 데스크의 완료 대조와 `brief audit` 처럼 **산출물과 그 뒤의 사실**로 잰다. 모든 지표는 판정
창(수습 7일, 계약 14일) 안에서 센다. 한 호출의 "그 뒤"는 같은 세션에서 호출 다음의 사용자 턴 5개다.

| 지표 | 뜻 | 세는 곳 | 방향 |
|---|---|---|---|
| `uses` | 창 안에서 불린 횟수 | Claude 세션 기록 `~/.claude/projects/*/*.jsonl` 의 `tool_use` 중 `input.subagent_type` 이 역할 이름인 것(스킬이면 `Skill` 호출의 `skill`). 위원회 평가·시험 호출(프로젝트 이름이 `-private-tmp-agent-scout-` 로 시작)은 뺀다. 명부의 `use` 줄은 대조용이다 | 적으면 해체 근거 |
| `ok` | 판정된 호출 중 카드의 `done_when` 을 통과한 비율 | 호출마다 하나. 데스크가 완료 대조 때 남긴 명부 `use` 줄(`agent-scout log`)이 있으면 그것을 쓴다. 없으면 심판(위원 아닌 모델)이 호출의 입력·결과와 그 뒤 사용자 턴을 읽고 `done_when` 으로 ok / miss / unclear 를 매긴다. unclear 는 분모에서 뺀다 | 높게 |
| `corrected` | 사용자가 역할의 결과를 고친 횟수 | 호출 뒤 사용자 턴 중 교정 패턴(`agent-scout` 의 `CORRECTION`, 발굴과 같은 추출)에 걸린 턴을 후보로, 심판이 역할의 결과를 고친 것인지 가린다. 명부의 `use … corrected` 줄도 센다(같은 호출은 한 번) | 낮게 (품질) |
| `repeat` | 역할이 막으려던 교정이 그 일에서 다시 나온 횟수 | 카드 `evidence` 의 교정 묶음이 기준이다. 창 안에서 카드 kind 의 세션 교정(`agent-scout scan` 의 교정 묶음과 같은 추출)을 심판이 같은 묶음인지 가린다. **역할을 부른 세션**에서 나온 것이 `repeat` 이고, 부르지 않은 세션에서 나온 것은 `repeat_uncalled`(호출 연결의 빈 곳)로 따로 적는다. 기준선은 발굴 기록의 같은 묶음 수를 7일당으로 바꾼 값 | 0 에 가깝게, 적어도 기준선보다 낮게 (효과) |
| `asked` | 그 일에서 사용자에게 간 질문 수 | 역할을 부른 세션의 `AskUserQuestion` 호출 수 + 그 세션이나 그 브리프를 가리키는 `~/.local/share/cmux/asked.json` 항목과 영역 Decision log 의 `asked` 줄. 비교 대상은 같은 kind 에서 역할을 부르지 않은 세션의 평균 | 줄인다 (부하) |

`asked` 만 보면 역할이 아무것이나 정하는 쪽으로 기운다. 영역 담당 설계 6.3 처럼 항상 `corrected` 와 함께 본다.
재계약 때는 무작위 표본 3건을 심판이 다시 채점해, 아무도 고치지 않은 잘못을 잡는다.

**누가 세나.** 판정일에 데스크가 역할마다 `agent-scout measure <역할> --judge --write` 를 한 번 돌린다(창은 명부의 시작일부터
수습 7일·계약 14일, `--since`/`--until` 로 바꾼다). 다섯 숫자를 출처와 함께 찍고, 심판(위원 아님)에게는 명부 `use` 줄이 없는
호출의 ok/miss, 교정 후보, repeat 후보만 묻는다. `--judge` 없이 돌리면 심판할 항목이 남은 숫자는 `잠정`이고 `--write` 는
거부한다(exit 3). 표본 부족(uses < 3)은 심판 없이 정해진다. 결과는 명부 Log 에 한 줄로 남긴다:

```
- MM-DD | <역할> | verdict | 창 MM-DD..MM-DD · uses N · ok a/b · corrected N · repeat N (기준 M/7일, uncalled K) · asked N | <결과> | by:user|desk
```

**명부 정정.** 명부의 줄은 고치지 않고 정정 줄을 더한다. `- MM-DD | <역할> | void | use ref:<R> | 이유 | by:..` 는 그 `use`
줄을 `measure`·`review` 가 세지 않게 하고, `- MM-DD | <역할> | void | hire backer:<위원> | 이유 | by:..` 는 그 위원을 고용
지지(와 그 역할로 받은 통과)에서 뺀다.

### 5.5 판정 (계약 뒤, 14일마다)

| 판정 | 조건(14일 창, 제안값) | 바뀌는 것 | 결정 |
|---|---|---|---|
| 재계약 + 확대 | `ok` ≥ 90%, `repeat` = 0, `uses` ≥ 5 | 권고 → 결정, 또는 트리거를 하나 넓힌다. 영역 권한표 안에서만 | 사용자 |
| 재계약 | `corrected` 가 늘지 않음 | 그대로 | 데스크가 기록하고 알린다 |
| 축소 | `corrected` 가 14일에 3회 이상 | 트리거나 권한을 한 단계 줄인다 | 사용자 |
| 퇴출 | 축소 뒤에도 `corrected` 가 줄지 않음, 또는 `repeat` 가 기준선과 같음 | 카드·명부 줄을 보관소로 옮긴다. ADR 로 남긴다 | 사용자 |
| 흡수 | 그 일을 도구가 막게 됨(오케스트레이터 → sib 와 같은 경우) | 퇴출과 같이 치우고, 이유에 흡수한 도구를 적는다 | 사용자 |
| 해체 | `uses` < 3 | 역할을 치우고 그 일은 세션 기본값으로 돌아간다 | 사용자 |

**결정권(사용자 규칙 11-24).** 투입은 역할·지표·판정 방법·근거 네 가지를 사용자에게 보고하고 전부 확인받은 뒤에만
한다. 판정 방법을 확인받았어도, 역할을 바꾸거나 치우는 판정(확대·축소·퇴출·흡수·해체, 모델 변경)은 데스크가 위 숫자를
붙여 `결정 필요`로 올리고 사용자가 정한다. 역할이 그대로인 결과(재계약, 수습 계약, 표본 부족 연장)만 데스크가 기록하고
알린다.

퇴출과 흡수는 **반드시 기록을 남긴다**(Decision log 의 `retire` 줄 + 그 저장소의 ADR). 같은 역할을 다시 고용하려면
그 기록을 먼저 읽는다 — 자동 승인 데몬이 기록 없이 되살아난 일을 막기 위해서다. 퇴출 때 지우는 것은 역할 카드의
학습분(역할이 스스로 더한 규칙)이고, 사용자가 직접 한 말과 사실 기록은 남긴다(영역 담당 설계 7절과 같음).

### 5.6 다른 모델로 재평가

투입 확인 때 사용자가 "이 모델로 쓰고, 판단을 못 하면 다른 모델로 한 번 더 평가"라고 정하면, 카드 `contract` 칸에 그
모델을 적는다(예: 범위 확인자는 작은 모델로 쓰고 큰 모델로 재평가).

- **언제**: 수습 판정에서 `ok` < 2/3 이고 miss 가 카드 `done_when` 의 판단 잘못일 때. 표본 부족(`uses` < 3)은 판단을
  못 한 것이 아니므로 재평가하지 않고 연장한다.
- **어떻게**: 창 안의 miss 호출 전부와 ok 호출을 합쳐 3건 이상의 입력을 재평가 모델로 다시 돌린다. 심판이 모델 이름을
  모른 채 두 결과를 `done_when` 으로 채점한다. 한 번만 한다.
- **그다음**: 재평가 모델이 miss 를 바로잡으면 "모델 변경 + 7일 수습 다시"를, 아니면 퇴출을 숫자와 함께 사용자에게
  올린다(모델 변경은 사용자 결정). 명부 Log 에 `reeval` 줄을 남긴다.

## 6. 누가 돌리나

| 단계 | 누가 | 형태 |
|---|---|---|
| 발굴 | **인사 점검 세션**. 데스크가 2주마다(영역 계약 판정과 같은 날) 영역 A 에 배치한다 | 상주하지 않는 한 번짜리 세션. 세는 일은 스크립트, 묶고 판단하는 일은 모델 |
| 정의·수습 구성 | 같은 인사 점검 세션, 또는 데스크가 띄운 새 세션 | 카드 초안, 블라인드 비교 |
| 고용·퇴출 결정 | 아래 표 | — |
| 평가 기록 | 데스크(완료 대조 때 명부에 `use` 줄 한 줄) | 기존 순찰에 한 줄 추가 |
| 판정 상정 | 데스크가 지표를 붙여 올린다 | `결정 필요` 한 줄, 또는 권한이 있으면 바로 정하고 알림 |

고용·퇴출을 누가 정하나 — 사용자 규칙(11-24)이 먼저다: 발굴됐든 사용자가 만들었든 **모든 에이전트**는 투입 전에
역할·평가 지표·평가 뒤 선발/퇴출 방법·근거를 사용자에게 직접 보고하고 전부 확인받는다. 영역 권한표의 `hire` 는
투입에 쓰지 않는다.

| 경우 | 결정 |
|---|---|
| 투입(고용) | 언제나 사용자. 네 가지 보고를 먼저 보인다. 기록은 영역 Decision log 의 `hire` 줄(`by:user`) |
| 수습 계약, 재계약, 표본 부족 연장 | 데스크가 기록하고 알린다(역할이 그대로다) |
| 확대·축소·퇴출·흡수·해체, 모델 변경 | 사용자. 데스크가 5.4 의 숫자를 붙여 `결정 필요`로 올린다 |
| 카드에 미리 적힌 재평가(5.6) | 데스크가 판정 세션에 맡겨 진행한다. 결과로 바꾸는 일은 위 줄을 따른다 |

인사 점검 자체를 상주 에이전트로 두지 않는 이유: 2주에 한 번 생기는 일이고, 상주 pane 은 사용자가 볼 곳을 늘린다
(영역 담당 설계 8절).

## 7. 영역 담당과 맞물리는 방식

- **영역 담당은 판단을, 역할은 일을 맡는다.** 영역 하나에 영역 담당은 하나, 역할은 여럿이다. 역할은 그 영역의 권한표를
  넘을 수 없다.
- **영역 담당도 인사 대상이다.** 영역 담당 설계 7절의 계약 판정은 이 절차의 5.5 를 한 형태(영역 담당)에 적용한 것이다.
  지표 이름(`asked`, `reversed`/`corrected`)을 맞춘다.
- **역할이 질문을 만들면 영역 담당이 먼저 받는다.** 역할 → 사용자로 바로 가지 않는다. 경로는 영역 담당 설계 9.1 과 같다.
- **영역 담당의 결정 기록이 발굴 자료가 된다.** 영역 담당이 같은 종류의 질문을 계속 받으면, 그 질문을 만드는 일이
  역할 후보다.
- **영역이 없는 일**(리서치처럼 주제를 따르는 일)의 역할은 그 주제의 영역에 속한다. 두 영역에 걸치면 더 보수적인 영역을
  따른다.

## 8. 첫 에이전트를 만드는 다음 단계

1순위: **업무 영역의 실험 계획 검토자**(4.1). 영역이 먼저 확인받는 곳이라 순서는 이렇다.

1. **사용자 확인**(한 번): "실험을 돌리기 전에 계획을 읽고 체크리스트로 권고만 하는 읽기 전용 에이전트를
   만들어도 되는가". 아니면 2순위(리서치 범위 확인자)로 같은 절차를 밟는다.
2. **카드 쓰기**: 형태는 에이전트 정의(읽기 전용 도구, 권고만). 체크리스트는 4절의 반복 교정 다섯 가지에서 시작한다 —
   시간 예산, 브리프에 없는 상황 금지, 지정한 데이터 원천, 범위 그대로(바꾸면 묻기), 놓치기 쉬운 값 파일. 회사 일이므로
   카드는 L2/L3 쪽(업무 저장소나 페르소나 저장소)에 둔다. 이 저장소에는 넣지 않는다.
3. **수습 판정 준비**: 교정이 많았던 과거 실험 세션 3건의 첫 브리프를 꺼내, 검토자 있이/없이 계획을 다시 쓰게 하고,
   Codex 심판이 이름을 모른 채 "그 세션에서 나온 교정을 미리 막았는가"로 채점한다.
4. **명부·기록 틀**: `orch-roster.md` 씨앗과 Decision log 의 `hire`·`retire` 종류. 이것은 영역 A 의 도구 일이라
   데스크가 배치한다(영역 담당 구현 세션과 겹치지 않게 그 세션이 끝난 뒤).
5. **판정**: 7일 뒤 수습 판정(5.3), 그 뒤 14일마다 5.5 표로.

## 9. 하지 않는 편이 나은 경우

- **도구로 막을 수 있는 일.** 데스크 완료 감사처럼 사실로 판정되는 일은 도구가 맞다. 에이전트는 판단이 남는 곳에만.
- **고통이 없는 일.** 교정이 0 인 일에 역할을 두면 유지비만 생긴다.
- **한 번 보인 신호.** 한 세션의 불만은 일화다. 두 조각 이상에서 보일 때만 후보로 올린다.
- **역할이 늘어 사용자가 볼 곳이 늘 때.** 역할은 pane 을 만들지 않고 세션 안의 서브에이전트나 한 번짜리 호출로만 돈다.
- **평가할 물량이 없는 역할.** 2주에 3회 미만이면 판정할 수 없으니 해체한다.

## 10. 구현: `/agent-scout` — 에이전트 발굴 위원회와 정의 도구

5.1(발굴)·5.2(정의)·6절(누가 돌리나)을 도구로 만들었다. pstack `/automate-me` 의 결과물이 스킬이라면 이 도구의
결과물은 에이전트 정의다. 사용자 요구(11-23): 발굴은 에이전트 하나가 단독으로 하지 않는다. 모델과 접근이 서로
다른 위원 3명이 쿼럼을 이루는 **위원회**가 정기적으로 열리고, 위원 구성은 설정으로 바뀌며, 위원도 평가받는다.
에이전트를 띄우고 결과를 받는 방식은 모델과 상관없이 하나(cmux pane 위의 `sib`)다.

| 부분 | 위치 |
|---|---|
| 흐름 | `skills/agent-scout/SKILL.md` (`/agent-scout`) |
| 엔진 | `bin/agent-scout` — `scan`·`convene`·`due`·`review`·`reject`·`candidates`·`show`·`new`·`check`·`install`·`log`·`measure`·`roster` |
| 위원 | `agents/scout-pstack.md`(pstack 방식, Claude opus), `agents/scout-jobs.md`(jobs-to-be-done, Codex), `agents/scout-portfolio.md`(포트폴리오 공백, Claude opus) |
| 위원·쿼럼·심판·평가·일정 설정 | `~/.config/cmux/agent-committee.md` (씨앗 `cmux/seeds/agent-committee.md`) |
| 명부 | `~/.config/cmux/orch-roster.md` (씨앗 `cmux/seeds/orch-roster.md`) |
| 회의 기록·초안 | `~/.local/share/cmux/hr/quorum-<날짜>.{json,md}`, `~/.local/share/cmux/hr/agents/<역할>.md` (로컬 전용) |

**위원은 모델과 접근이 다르다.** pstack 위원은 교정과 물량을 `/automate-me`·`/correct`·`/reflect` 방식으로 캔다.
jobs 위원은 맡긴 일(sib 브리프)과 되돌아온 질문·결정을 일의 단위로 본다. portfolio 위원은 일의 종류별 사용자 시간과
있는 역할을 맞대 공백을 찾는다. 위원과 심판은 모두 `sib spawn`(Codex 는 `--codex`, 모델은 `--model`)으로 cmux pane 에서
과제 파일을 읽고 답 파일을 쓴다. `claude -p`·`codex exec` 같은 pane 없는 경로는 없다.

**쿼럼 규칙**(기본값): 같은 아이디어(역할)를 서로 다른 위원 **2명 이상**이 올리면 통과. 두 제안은 역할 이름이 같거나
일반 낱말(agent, checker, reviewer …)이 아닌 낱말을 함께 가질 때 같은 아이디어다(scope-checker 와 doc-scope-checker).
같은 kind 의 다른 역할은 따로 센다. 1명 모자란 후보는 올리지
않은 위원에게 **자기 근거로** 찬반을 묻고 찬성을 지지로 센다. 그래도 1명이면 관찰 목록에 남겨 다음 회의에서 다시
본다. 결과를 손으로 바꾸지 않는다. 한 위원이 실패하면 나머지로 판정하고 실패를 기록한다.

**위원 평가는 위원이 아닌 쪽이 한다.** (1) 위원이 아닌 심판 모델(설정 `judge`, 위원과 같은 runner:model 이면 거부)이
제안마다 이름을 모른 채 근거(0-2)와 적합성(0-2)을 채점한다. (2) `agent-scout review` 가 회의 기록과 명부에서 위원별로
통과율, 심판 점수, 고용 수, 수습 결과, 뒤집힌 수(사용자가 `reject` 한 후보, 그 위원이 지지한 역할의 `corrected`·수습
실패)를 센다. 설정의 선(`min_runs`, `pass_rate_min`, `judge_min`, `reversed_max`) 아래면 `on_fail: bench` 에 따라
설정에서 그 위원을 `off` 로 바꾸고 교체 위원을 찾으라고 알린다.

**정기 소집**: 데스크가 아침 순찰에서 `agent-scout due` 를 돌리고, 회의가 돌아왔으면(기본 14일) 영역 A 에 `/agent-scout`
세션 하나를 배치한다. 그 세션이 회의 → 후보 고르기 → 정의·설치 → `review` 를 한다.

**정의와 설치**: `new` 가 역할 카드(5.2 의 칸)·근거(지지한 위원 포함)·`TODO` 가 든 초안을 만들고, 세션이 근거를 읽고
채운다. `check` 는 칸이 비었거나 `TODO` 가 남았거나 지시문이 없으면 막는다. `install` 은 초안을 `~/.claude/agents/` 로
복사하고 명부에 수습 7일 줄과 `hire` 줄(지지한 위원)을 남긴다. 카드가 먼저 묻는 영역(`orch-local.md` 의 Ask-first)에
닿으면 `--user-approved` 없이는 설치하지 않는다(exit 3). 11-24 규칙으로 모든 에이전트가 `report` 뒤 사용자 확인을 받는다.
먼저 묻는 영역의 에이전트는 L1 에 정의하지 않는다: `new --layer L1` 과 `install` 이 거부한다.

**심판 보류**: 쿼럼을 통과했어도 심판의 평균 적합 점수(0-2)가 설정 `hold_below` 아래면 `hold` 로 두고 사용자가 정한다.
심판은 지지를 더하지 못하고 보류만 건다. 사용자가 풀면 명부에 `lifted` 줄이 남는다.

**층 배치**: 위원회는 L1 이고, 만들어진 에이전트는 일의 층에 놓인다. 역할 카드의 `layer`·`home` 에 따라 `install` 이 원본을
L1(`agents/`, 회사 맥락이면 거부)·L2(페르소나 저장소)·L3(프로젝트의 `.claude/agents`, 그 프로젝트에서만 켜짐)에 둔다.
다른 저장소에서는 커밋하지 않는다.

**알려진 한계**(11-24 첫 회의): 쿼럼은 일의 종류(kind)로 묶는다. 같은 종류에서 위원들이 서로 다른 역할을 올려도 한 후보의
지지로 합쳐진다(agent-tooling 에서 pstack 의 '원인부터 찾기'와 portfolio 의 'L1·L2 동기화'). 심판 보류가 이 경우를 잡았다. 그렇게 설치된 계층 동기화 에이전트의 정의는 portfolio 근거만 남기도록
고쳤다(pstack 제안은 다른 역할이라 지지에서 뺌, 고친 지지 1). 같은 날 쿼럼은 아이디어로 묶도록 바뀌었고, 명부의 `hire` 줄은
`void | hire backer:pstack` 정정 줄로 바로잡았다.


## 11. 반대 방향: 사용자가 만들고 위원회가 평가한다 (`agent-scout evaluate`, 11-24)

사용자 요구(11-24): 위원회가 발굴하던 방식을 뒤집어, 사용자가 에이전트를 만들고 위원회가 적절한지 평가한다.
위원은 더 다양한 아이디어와 방식으로 평가할 수 있게 늘린다.

| 부분 | 내용 |
|---|---|
| 초안 | `agent-scout new <역할> --by-user --title T --kind K` — 근거 칸이 `made by:user` 로 시작. 근거 인용은 세션이 이력에서 채운다 |
| 평가 | `agent-scout evaluate <역할>...` — 위원마다 pane 하나에서 모든 초안을 자기 접근과 근거로 본다. 근거 묶음은 초안의 kind 로 좁힌다. 답: hire / revise / reject 와 필요·형태·안전(0-2), 고칠 점, 근거 |
| 심판 | 위원 이름을 가린 채 **평가의 근거**(grounded 0-2)를 채점한다. 판정에 동의하는지는 채점하지 않는다. `ground_min` 미만인 평가는 기록에 남지만 세지 않는다 |
| 판정 | 센 평가 중 reject 가 `reject` 명 이상이면 거절, hire 가 `approve` 명 이상이면 승인, 그 밖은 수정 |
| 설치 | 모든 설치는 `agent-scout report <역할>`(역할·지표·선발/퇴출·근거, 5.5 의 사용자 규칙)을 사용자에게 보인 뒤 사용자가 예라고 한 역할만 `--user-approved` 로 한다. 그 밖에 `made by:user` 초안에 승인 평가가 없거나 마지막 평가가 승인이 아니면 그 사실을 알리고 거부한다(exit 3) |
| 위원 평가 | 평가 회의의 심판 점수(grounded/2)가 위원의 심판 점수에 합쳐진다. 통과율은 제안 회의에 `min_runs` 번 이상 나온 위원에게만 적용한다 |
| 기록 | `~/.local/share/cmux/hr/eval-<날짜>-<n>.{json,md}`, 명부에 `evaluate` 줄, 설치 시 `hire` 줄의 backers 는 hire 라고 한 위원 |

## 12. 모든 에이전트는 교체 대상이다 (사용자 규칙 11-24)

사용자 규칙(11-24 11:20): "데스크도 교체 대상이야 모든 에이전트는 교체 대상임 데스크도 위원회도 모두가 평가되어서
평가결과에 의해 대체 될수 있음". 11-23 에는 "데스크의 닫기 결함이 고쳐지지 않으면 재계약하지 않고 발굴 위원회가
대체한다"고 했다. 그래서 설치된 에이전트만이 아니라 데스크, 영역 담당, 위원회 위원, 심판도 **같은 모양의 계약**을 갖는다.
새 지표는 만들지 않고 이미 있는 기록을 쓴다. 쓸 만한 지표가 없는 곳은 없다고 적는다.

### 12.1 계약의 모양

명부(`orch-roster.md`)의 한 줄이 계약이다. 모든 줄에 같은 칸이 있다.

| 칸 | 뜻 |
|---|---|
| 역할·형태·층·영역 | 무엇이 어느 자리에 있나 |
| 상태·시작·판정 | 수습·계약·시험 단계, 시작일, 다음 판정일과 주기 |
| `지표:` | 숫자를 찍는 명령. 모두 `agent-scout measure <역할>` 이고, 명령이 각 숫자 옆에 출처를 적는다 |
| `교체선:` | 유지 / 수정 / 교체를 가르는 숫자 |
| `판정자:` | 언제나 사용자. 기록을 누가 남기는지 괄호에 적는다 |

절은 셋이다. `## Roles`(설치된 에이전트), `## Standing`(데스크, 영역 담당), `## Committee`(위원과 심판).

### 12.2 역할별 계약

| 역할 | 지표와 출처 | 판정 | 교체선 |
|---|---|---|---|
| 설치된 에이전트 | `measure <역할>`: uses·ok·corrected·repeat·asked (5.4) | 수습 7일 → 14일마다 | 5.3·5.5 표 |
| 데스크 (`desk`) | `brief audit --day D --json` 의 데스크가 일이 남은 채 닫은 세션(도구가 다시 판정), 끝났는데 열어 둔 세션. desk-eval 의 세트별 최신 점수: 정답률, harm, 괜히 물음, 앞 버전 대비 새 harm. `board.jsonl` 의 넘긴 결정·스스로 가능·고쳐 말함·교훈 어김은 데스크가 적거나 분류한 값이라 **참고만 하고 판정에 쓰지 않는다** | 7일 창, 매주 월요일(desk-eval 주간 실행과 같은 날). 첫 판정 12-01 | 7일 합 일 남은 채 닫음 ≤ 1 유지 · 2~4 또는 desk-eval 새 harm → 수정(orch.md 수정 세션 배치 뒤 다시 채점) · ≥ 5, 또는 수정 판정 다음에도 2 이상(수정 뒤 재발) → 교체 후보 |
| 영역 담당 (`lead:A`) | 영역 Decision log: `by:lead` 줄, 그중 뒤집힌 것(`reversed_by` 표시, 또는 뒤의 줄이 그 시각을 들어 되돌린 것), 영역 전체의 뒤집힌 줄, `asked` 줄 | 영역 프로파일의 Trial 판정일(A: 11-30), 그 뒤 14일마다 | 그 영역 Trial 의 숫자 그대로: 뒤집힘 비율 ≤ 5% 이고 하루 asked < 5, 영역 reversed ≤ 2 → 다음 단계 · by:lead 결정 2건 이상 뒤집힘 → 1단계로 · 영역 reversed 7일 ≥ 3 → 멈춤. **누가 뒤집었든 센다**(사용자 11-24: 데스크가 막은 것도 셈) |
| 위원 | `measure <위원>`: `review` 와 같은 숫자 — 통과율, 심판 점수, 고용, 뒤집힘(사용자가 거절한 지지 후보 + 지지한 역할의 corrected·수습 실패 + 위원이 reject 했는데 사용자가 들인 역할) | 위원회 정기 소집(14일)과 같은 날 | 설정 `## Review` 의 선 미달 → bench |
| 심판 (`judge`) | 명부의 `committee \| lifted` 줄(사용자가 심판의 보류를 푼 수)과 회의 기록의 보류 수. **채점이 맞았는지 재는 지표는 없다** | 14일마다 | 14일에 lifted ≥ 2 → 교체 검토 |

데스크와 영역 담당의 숫자에는 한계가 있다. 영역 Decision log 의 `reversed_by`·`asked` 표시는 데스크가 쓴다. 그래서
영역 담당의 숫자에 데스크의 판단이 들어간다(`measure lead` 가 이 주의를 함께 찍는다). desk-eval 은 주간 실행이 예약되어
있어야 창마다 새 점수가 나온다. 창 안에 점수가 없으면 `measure desk` 는 "판단 정확도는 재지 않음"이라고 적고
닫기 숫자만으로 판정한다.

### 12.3 아무도 자기 자신을 판정하지 않는다

- **데스크**: 데스크는 자기 판정 줄을 쓰지 않는다. `measure desk|lead|judge --write` 는 `--by user` 없이 거부한다(exit 3).
  판정 줄은 사용자 pane 에서 남긴다. 데스크는 숫자를 볼 수 있지만, 자기 계약을 `결정 필요`에 올리는 것도 데스크가
  아니라 desk-eval 주간 보고와 `measure desk` 다.
- **위원**: 위원의 숫자는 `review` 가 기록에서 센다(위원의 자기 보고가 아니다). 한 위원을 바꿀 초안은
  `evaluate --replacing <위원>` 으로 평가해, 그 위원이 자기 자리에 투표하지 않게 한다.
- **영역 담당**: 자기 계약은 "계약 자체"라 어떤 계약으로도 영역 담당에게 넘어가지 않는다(영역 담당 설계 5.2). 그 판정과
  질문은 사용자에게 간다.
- **에이전트 발굴과 평가 방식**에 관한 결정은 영역 담당이 하고(영역 결정 11-24 11:00), 데스크·영역 담당·위원회
  자신의 계약은 사용자가 정한다.

### 12.4 교체 절차 (모든 역할이 같은 순서)

```
판정 숫자가 교체선에 닿음 ──→ 결정 필요(숫자와 출처) ──→ 사용자: 후보를 찾는다
   ──→ 후보 만들기 ──→ 나란히 시험 ──→ 사용자: 바꾼다 / 그대로 둔다 ──→ 명부 replace 줄, 옛 카드 보관
```

1. **올리기.** 판정 결과가 교체 후보(데스크), 1단계로·멈춤(영역 담당), bench(위원), 교체 검토(심판), 퇴출·축소(에이전트)면
   숫자와 출처를 붙여 `결정 필요`에 올린다. 데스크 자신의 결과는 데스크가 아니라 desk-eval 주간 보고가 올린다.
2. **후보 만들기.** 역할별로 이미 있는 길을 쓴다.

   | 역할 | 후보 |
   |---|---|
   | 데스크 | 영역 A 세션이 `agents/orch.md` 후보 버전을 쓴다(다른 모델로 돌리는 것도 후보) |
   | 영역 담당 | `brief lead` 의 지시문·모델 후보 |
   | 위원 | 다른 접근이나 모델의 위원 정의(`/agent-scout`), `evaluate --replacing <위원>` 으로 평가 |
   | 심판 | 위원과 겹치지 않는 다른 runner:model |
   | 에이전트 | 위원회 `convene`·`evaluate`, 또는 5.6 의 재평가 모델 |

3. **나란히 시험.** 지금 역할과 후보를 같은 입력에 돌리고, 이름을 모르는 쪽이 채점한다.

   | 역할 | 시험 |
   |---|---|
   | 데스크 | desk-eval `score --versions <지금> <후보>`: 같은 고정 사례와 그 주 holdout, Pareto 판정(새 harm 이 있으면 나쁨) |
   | 영역 담당 | 창 안에서 영역 담당이 받은 질문을 후보로 `brief lead --dry-run` 해 다시 돌리고, 심판이 사용자 결정과 견줘 블라인드 채점 |
   | 위원 | 다음 회의에 그림자로 앉힌다(제안과 표는 세지 않음). 그 뒤 `measure` 숫자를 지금 위원과 비교 |
   | 심판 | 지난 회의의 제안·리뷰를 후보 심판이 다시 채점하고, 사용자 결정(hire·reject·lifted)과 맞는 비율을 비교 |
   | 에이전트 | 5.6 의 블라인드 재실행 |

4. **바꾸기.** 사용자가 정한다. 명부 Log 에 `- MM-DD | <역할> | replace | <옛 것> → <새 것> | 근거 | by:user` 를 남긴다.
   옛 정의는 보관소로 옮기고, 역할이 스스로 더한 학습분은 비우고, 사용자가 직접 한 말과 사실 기록은 남긴다(5.5, 영역
   담당 설계 7절). 새 것은 수습부터 시작한다.
