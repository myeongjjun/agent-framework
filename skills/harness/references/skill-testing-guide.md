## 1. Testing Framework Overview

Skill quality is validated through a combination of **qualitative** and **quantitative** evaluation.

| Type | Method | Best for |
|------|--------|----------|
| **Qualitative** | User reviews output directly | Subjective quality: tone, design, creative work |
| **Quantitative** | Assertion-based automated grading | Objective verification: file creation, data extraction, code generation |

Core loop: **Write -> Test -> Evaluate -> Improve -> Re-test**

## 2. Test Prompt Design

### Principles

Test prompts must be **realistic, specific, and natural** -- the kind of thing a real user would actually type. Abstract or artificial prompts have low test value.

**Bad:** `"Process the PDF"`, `"Extract data"`, `"Generate chart"`

**Good:** `"Extract the table on page 3 of this PDF and convert to CSV. The table header spans 2 rows -- first row is category, second is actual column names."`

### Diversity

Mix along these dimensions:
- **Tone:** formal and casual
- **Intent:** explicit ("convert this PDF table") and implicit (context-dependent)
- **Complexity:** simple single-step and complex multi-step
- Include some abbreviations, typos, and casual phrasing

### Coverage

Start with 2-3 prompts covering:
- 1 core use case
- 1 edge case
- (Optional) 1 compound task

## 3. Execution Testing: With-skill vs Baseline

### Comparison Setup

For each test prompt, spawn two sub-agents **simultaneously**:

**With-skill:**
```
Prompt: "{test prompt}"
Skill path: {skill path}
Output path: _workspace/iteration-N/eval-{id}/with_skill/outputs/
```

**Baseline (without skill):**
```
Prompt: "{same test prompt}"
Skill: none
Output path: _workspace/iteration-N/eval-{id}/without_skill/outputs/
```

### Baseline Selection

| Situation | Baseline |
|-----------|----------|
| New skill | Same prompt without any skill |
| Improving existing skill | Prior version of the skill (preserve snapshot) |

### Timing Data Capture

Save `total_tokens` and `duration_ms` from the sub-agent completion notification **immediately**. This data is available only at notification time and cannot be recovered later.

## 4. Quantitative Evaluation: Assertion-based Grading

### Writing Assertions

When outputs are objectively verifiable, define assertions for automated grading.

**Good assertions:**
- Objectively true/false determinable
- Descriptive text that makes pass/fail clear at a glance
- Tests the skill's core value proposition

**Bad assertions:**
- Always passes regardless of skill presence (e.g., "output exists")
- Requires subjective judgment (e.g., "well-written")

### Programmatic Verification

When assertions can be verified by code, write verification scripts. They are faster, more reliable, and reusable across iterations.

### Non-discriminating Assertions

If an assertion passes 100% for both with-skill and without-skill, it does not measure the skill's differential value. Remove or replace with a more challenging assertion.

### Grading Schema

```json
{
  "expectations": [
    {
      "text": "Profit margin column added",
      "passed": true,
      "evidence": "Column E contains 'profit_margin_pct'"
    },
    {
      "text": "Sorted by profit margin descending",
      "passed": false,
      "evidence": "Original row order preserved, no sorting applied"
    }
  ],
  "summary": {
    "passed": 1,
    "failed": 1,
    "total": 2,
    "pass_rate": 0.50
  }
}
```

## 5. Specialized Evaluation Agents

### Grader

Performs assertion-based grading. Extracts verifiable claims from outputs and cross-checks them.

**Responsibilities:**
- Per-assertion pass/fail judgment with evidence
- Extract factual claims from outputs and verify
- Meta-feedback on eval quality (flag assertions that are too easy or ambiguous)

### Comparator (Blind Comparison)

Anonymizes two outputs as A/B and judges quality without knowing which used the skill.

**Use when:** You need rigorous confirmation that the new version is actually better. Skippable during routine iteration.

**Judgment criteria:** Content accuracy, completeness, structural organization, formatting, usability.

### Analyzer

Analyzes benchmark data for statistical patterns:
- Non-discriminating assertions (both configs pass -- no differential value)
- High-variance evals (results vary significantly between runs -- instability)
- Time/token tradeoffs (skill improves quality but at what cost?)

## 6. Iterative Improvement Loop

### Feedback Collection

Show outputs to the user and collect feedback. Empty feedback means "no issues."

### Improvement Principles

1. **Generalize feedback** -- narrow fixes for specific test inputs are overfitting. Fix at the principle level.
2. **Remove dead weight** -- read transcripts; if the skill causes agents to do unproductive work, delete that part.
3. **Explain why** -- even when user feedback is terse, understand the underlying concern and embed that understanding into the skill.
4. **Bundle repeated work** -- if every test run generates the same helper script, pre-bundle it in `scripts/`.

### Iteration Procedure

```
1. Modify skill
2. Re-run all test cases in new iteration-N+1/ directory
3. Present results to user (compare with prior iteration)
4. Collect feedback
5. Modify again -> repeat
```

**Termination conditions:**
- User is satisfied
- All feedback is empty (no issues found)
- No meaningful further improvements possible

### Draft-Revise Pattern

When modifying skills, write a draft first, then re-read with fresh eyes and improve. Do not try to write perfectly in one pass.

## 7. Description Trigger Validation

### Writing Trigger Eval Queries

Prepare 16-20 eval queries: ~10 should-trigger + ~10 should-NOT-trigger.

**Quality criteria:**
- Realistic, specific, natural language
- Include concrete details (file paths, column names, company names)
- Mix length, tone, and formality
- Focus on **boundary cases** over clear-cut ones

**Should-trigger (8-10):**
- Same intent expressed in different ways (formal/casual)
- Intent is clear but skill/file type is not explicitly mentioned
- Niche use cases
- Cases where this skill should win over competing skills

**Should-NOT-trigger (8-10):**
- **Near-misses are key** -- similar keywords but different intent/domain
- Clearly unrelated queries (e.g., "write a Fibonacci function") have zero test value
- Adjacent domains, ambiguous phrasing, keyword overlap with different context

### Existing Skill Conflict Check

1. Collect descriptions of all existing skills
2. Verify that new skill's should-trigger queries do not accidentally trigger existing skills
3. If conflicts found, sharpen boundary conditions in the description

### Automated Optimization (Optional Advanced)

For mature skills where trigger accuracy matters:
1. Split 20 eval queries into Train (60%) / Test (40%)
2. Measure trigger accuracy with current description
3. Analyze failures, generate improved description
4. Select best description based on **Test set** (not Train -- avoid overfitting)
5. Max 5 iterations

> This process uses `claude -p` for automation. High token cost -- run only after the skill is stabilized, as a final polish step.

## 8. Workspace Structure

Directory structure for systematic test/evaluation management:

```
{skill-name}-workspace/
+-- iteration-1/
|   +-- eval-descriptive-name-1/
|   |   +-- eval_metadata.json
|   |   +-- with_skill/
|   |   |   +-- outputs/
|   |   |   +-- timing.json
|   |   |   +-- grading.json
|   |   +-- without_skill/
|   |       +-- outputs/
|   |       +-- timing.json
|   |       +-- grading.json
|   +-- eval-descriptive-name-2/
|   |   +-- ...
|   +-- benchmark.json
+-- iteration-2/
|   +-- ...
+-- evals/
    +-- evals.json
```

**Rules:**
- Eval directories use **descriptive names**, not numbers (e.g., `eval-multi-page-table-extraction`)
- Each iteration lives in its own directory (never overwrite prior iterations)
- `_workspace/` is never deleted -- preserved for audit trail and post-hoc analysis
